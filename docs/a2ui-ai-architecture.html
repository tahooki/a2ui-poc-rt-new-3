A2UI AI Architecture

AI-Driven DevOps Console — 사용자 입력부터 Surface 렌더링까지의 전체 흐름

1 전체 흐름 개요
사용자의 채팅 입력이 AI/규칙 기반으로 처리되어 Template Surface로 렌더링되기까지의 흐름입니다.
User
채팅 입력
사용자가 "payments-api 배포해줘" 같은 자연어를 입력
API
POST /api/chat
SSE 스트림으로 전송. facts, intent, workflow 상태 포함
Core
Orchestrator
8단계 파이프라인 실행 (intent, slot, tool, decision)
Decision
정책 평가
text / ask_followup / render_surface 중 하나 결정
Output
Surface 렌더
Template 선택 → Binder → React 컴포넌트 렌더링
2 Orchestration Pipeline
orchestrate-chat-turn.ts — 모든 채팅 턴의 핵심 처리 파이프라인입니다. 최대 3회 반복(MAX_ITERATIONS)합니다.
Step 1
State Hydration
요청으로부터 facts, intent, workflow, awaiting 상태를 복원합니다.
Step 2
Awaiting 응답 처리
이전 턴에서 사용자에게 질문(awaiting)한 경우, 응답을 파싱합니다.
AI 모드 LLM이 fill_slot / cancel / correction / interrupt 분류
Mock 모드 규칙 기반 엔터티 매칭 & 유효성 검증
Step 3
Intent & Workflow 해석
사용자 입력에서 Intent(의도)를 추출하고 Workflow 상태를 업데이트합니다.
AI 모드 LLM이 intent 분류 + slot 값 추출
Mock 모드 정규식 패턴 매칭 + carry 정책
Step 4-6
Tool 계획 & 실행 루프
Intent + 현재 Slot 상태를 보고 필요한 Tool을 계획하고 실행합니다.
planTools() → executeTool() → adaptToolResult()
Tool 결과는 facts와 slot에 병합되어 다음 반복에 사용됩니다.
Step 7
Decision 평가
Intent별 정책 평가기(Policy Evaluator)가 최종 결정을 내립니다.
text 텍스트 응답 ask_followup 추가 질문 render_surface 템플릿 렌더
Step 8
응답 생성
Decision 결과에 따라 최종 응답을 구성합니다.
ask_followup: 누락 slot의 awaiting 계약 생성
render_surface: Template 선택 → Binder → SurfaceEnvelope
text: LLM 또는 Mock 텍스트 응답
3 Slot 시스템
대화를 통해 수집되는 정보 조각(Slot)을 관리합니다. 의존성 추적과 무효화를 지원합니다.
Slot 정의 구조
slot-definitions.ts
SlotDefinition { slotKey: "deploy.serviceName" type: "string" | "enum" | "list" required: true sourcePrecedence: ["user", "selection", "tool"] validValues?: ["production", "staging"] staleWhen?: ["deploy.serviceName"] awaitingInput?: "single_select" awaitingPrompt?: "어떤 서비스를?" }
Intent별 필수 Slot
각 Intent가 동작하기 위해 필요한 Slot 목록
IntentRequired SlotsReady Set
deploy.start serviceName serviceName + selectedServiceContext
approval.review requestId requestId + queueItems
rollback.start serviceName serviceName + candidates
Slot 우선순위 & 무효화
Source Precedence (높은 순)
1 user — 사용자가 직접 입력한 값
2 selection — UI에서 선택한 값
3 tool — Tool 실행 결과
4 system — 시스템 기본값
staleWhen 의존성 예시
deploy.environment는 serviceName 변경 시 무효화
deploy.selectedServiceContext는 serviceName 변경 시 무효화
서비스를 바꾸면 환경/컨텍스트가 자동 초기화됨
4 Decision Engine
Intent별 정책(Policy)에 따라 3가지 모드 중 하나를 결정합니다.
Deploy Policy 판단 흐름
policies/deploy.ts
조건 1
deploy.serviceName 슬롯이 비어있는가?
Yes → ask_followup
"어떤 서비스를 배포할까요?" 질문 + 서비스 목록 조회 Tool 실행
조건 2
serviceName 있지만 selectedServiceContext 없는가?
Yes → ask_followup (+ Tool)
getServiceDeployContext Tool 실행 후 다시 평가
조건 3
모든 Ready Set 슬롯이 채워졌는가?
Yes → render_surface
QuickDeployLaunchpad 템플릿 렌더링
text
일반 질문에 대한 텍스트 응답. LLM 또는 Mock 패턴 매칭으로 생성.
ask_followup
필수 Slot이 누락. 사용자에게 추가 정보 요청. single_select / free_text 입력 방식.
render_surface
모든 조건 충족. Template 선택 → Binder 실행 → Surface 카드 렌더링.
5 Tool 시스템
Intent와 Slot 상태를 기반으로 필요한 데이터를 수집하는 도구입니다. Seed JSON 데이터를 조회합니다.
Tool트리거 조건반환 데이터Slot 업데이트
getDeployableServices deploy intent + serviceName 없음 배포 가능 서비스 목록 deploy.availableServices
getServiceDeployContext deploy intent + serviceName 있음 서비스 설정, 환경, 이미지 목록 deploy.selectedServiceContext
getPreviousDeployments deploy.history.lookup intent 이전 배포 이력 deploy.deployHistory
getApprovalQueueSummary approval intent 승인 대기 요청 목록 approval.queueItems
getRollbackCandidates rollback intent 롤백 대상 목록 rollback.candidates
Tool 실행 흐름
// 1. Tool 계획 planTools(intentKey, facts) → deploy.start + no serviceName → ["getDeployableServices"] → deploy.start + serviceName → ["getServiceDeployContext"] // 2. 중복 제거 deduplicateTools(planned, alreadyExecuted) // 3. 실행 executeTool(toolDef, facts, contextSnapshot) → ToolOutput { ok, data, summary } // 4. 결과 적용 adaptToolResult(output) → { factsPatch, slotPatch } // facts + slots에 병합
6 Template 시스템
Decision이 render_surface를 반환하면, 적절한 Template을 선택하고 데이터를 바인딩하여 UI로 렌더링합니다.
Template 선택 (Scoring)
template-selector.ts
scoreCandidate(definition, input) { intentMatch: intentKeys에 현재 intent 포함? familyMatch: surfaceIntent.family 일치? +2점 requiredFacts: 모든 필수 facts 존재? +1점 // 최고 점수 Template 선택 return candidates.sort(byScore)[0] }

7 AI / Mock 모드 전환
헤더의 토글 버튼으로 AI(LLM) 모드와 Mock(규칙 기반) 모드를 전환합니다.

AI 모드 LLM 기반

Intent 해석: LLM이 자연어에서 intent + slot 값 추출
Awaiting 처리: LLM이 fill_slot / cancel / correction 분류
응답 생성: Tool 결과를 LLM이 자연어로 변환
요구사항: OPENAI_API_KEY 환경변수 필요
VS

Mock 모드 규칙 기반

Intent 해석: 정규식 패턴 매칭 (triggerPatterns)
Awaiting 처리: 엔터티 매칭 + validValues 검증
응답 생성: mock-responses.ts 패턴 DB에서 매칭
요구사항: 없음 (API 키 불필요)
모드 분기 로직
const forceMock = useAi === false if (isLlmAvailable() && !forceMock) { // AI 경로: LLM 호출 resolveAwaitingWithAi(input) // Step 2 resolveIntentWithAi(input) // Step 3 callLlmOrFallback(prompt) // Step 8 } else { // Mock 경로: 규칙 기반 resolveAwaiting(input) // Step 2 resolveIntent(input) // Step 3 findMockResponse(input, pageKey) // Step 8 }
8 상태 관리 (Zustand)
두 개의 Zustand Store가 대화 상태와 UI 상태를 각각 관리합니다.
ConversationStore
대화 단위 상태 (conversation-store.ts)
messages: 채팅 메시지 목록 (max 40)
intent: 현재 활성 Intent
workflow: 워크플로우 진행 상태
facts: 수집된 Slot 값들
awaiting: 사용자 응답 대기 계약
activeSurface: 렌더 중인 Template
composerText: 입력창 텍스트
주요 액션: startUserTurn, appendAssistantDelta, completeAssistantTurn, mergeFacts, setActiveSurface
AppStore
페이지 단위 UI 상태 (app-store.ts)
pages: deploy / approve / rollback 페이지 데이터
deployWorkflow: Image/Request 폼 상태
images: 등록된 Docker 이미지 목록
items: 배포 요청/실행 항목
selectedRow: 테이블 선택 행
sidebarOpen: 사이드바 상태
주요 액션: registerDeployImage, submitDeployRequest, startDeployRun, completeDeployRun
9 E2E 시나리오: "payments-api 배포해줘"
실제 사용자 대화가 처리되는 전체 과정을 단계별로 추적합니다.
Turn 1 — 사용자 입력
"payments-api 배포해줘"
Step 3: Intent → deploy.start, Slot 추출 → serviceName = "payments-api"
Step 4: Tool 계획 → getServiceDeployContext("payments-api")
Step 5: Tool 실행 → 환경, 이미지, 버전 정보 반환
Step 6: Slot 업데이트 → selectedServiceContext 채워짐
Step 7: Deploy Policy → Ready Set 완성 → render_surface
Step 8: Template 선택 → QuickDeployLaunchpad → Binder 실행
