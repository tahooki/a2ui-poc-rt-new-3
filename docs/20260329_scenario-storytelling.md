# A2UI DevOps Assistant — 시나리오 스토리텔링

> 실제 DevOps 엔지니어의 하루를 따라가며, AI 어시스턴트가 어떻게 업무를 바꾸는지 보여드립니다.

---

## 등장인물

| 이름 | 역할 | 주요 업무 |
|------|------|----------|
| **김배포** 선임 | Platform Engineer | 서비스 배포 담당, 매일 2~3회 production 배포 |
| **이승인** 팀장 | DevOps Team Lead | 승인 큐 관리, 고위험 요청 검토 |
| **박롤백** 대리 | SRE (Site Reliability Engineer) | 인시던트 대응, 롤백 실행 |

---

## Episode 1. 김배포 선임의 월요일 아침 — "배포"

### 매일 아침, 같은 루틴

김배포 선임은 매일 아침 9시에 출근하면 똑같은 일을 반복합니다. 콘솔을 열고, 서비스 목록을 스크롤하고, 버전을 확인하고, preflight check을 돌리고, 배포 버튼을 누릅니다. 서비스가 12개. 환경이 3개. 매번 수십 번의 클릭.

> **김배포:** "지난주에 payments-api 마지막으로 배포한 게 언제였더라… 이력 페이지 들어가서 필터 걸고 찾아야 하나."

그는 배포 이력 페이지로 이동하고, 서비스 필터를 선택하고, 날짜 범위를 조정합니다. 이미 3분이 지났습니다. 겨우 한 줄의 정보를 얻기 위해서.

### AI 어시스턴트가 있다면

```
👤 김배포: payments-api 마지막 배포 언제였어?
🤖 AI: payments-api의 마지막 배포는 2026-03-25이며, v2.3.18-rc1 버전이
       production 환경에 rolling 전략으로 배포되었습니다.
```

**3분이 3초로.** 페이지 이동도, 필터 설정도, 스크롤도 없습니다.

### 이제 배포를 시작합니다

김배포 선임은 오늘 payments-api의 신규 버전을 배포해야 합니다. 기존이라면 — 서비스 선택 드롭다운 클릭, 환경 선택, 이미지 목록 로딩 대기, 버전 선택, preflight check 실행, 결과 확인, 최종 배포 버튼 클릭. **7단계, 최소 2분.**

```
👤 김배포: 배포하고 싶어
🤖 AI: 어떤 서비스를 배포할까요?
       [payments-api]  [checkout]  [catalog-api]

👤 김배포: payments-api
🤖 AI: payments-api 배포 컨텍스트 — 이미지 1건, 추천 버전 v2.3.18-rc1.
       필요한 정보가 모두 준비되었습니다.
       ┌──────────────────────────────┐
       │   Quick Deploy Launchpad     │
       │   [배포 시작]                 │
       └──────────────────────────────┘
```

**대화 2턴으로 배포 화면까지 도달.** 더 빠른 사람은 한 턴에 끝냅니다:

```
👤 김배포: payments-api 배포해줘
🤖 AI: (서비스 자동 인식 → 컨텍스트 즉시 조회)
       필요한 정보가 모두 준비되었습니다.
       ┌──────────────────────────────┐
       │   Quick Deploy Launchpad     │
       │   [배포 시작]                 │
       └──────────────────────────────┘
```

### 도중에 마음이 바뀌면?

김배포 선임이 서비스를 고르다가 "아, 잠깐 이거 말고 orders-api"라고 합니다. 기존 콘솔이라면 뒤로 가기 → 다시 선택. AI 어시스턴트는?

```
👤 김배포: 아니 orders-api
🤖 AI: orders-api로 변경합니다.
```

**정정도, 취소도, 도메인 전환도 자연어 한 마디로.**

```
👤 김배포: 취소해줘
🤖 AI: 취소했습니다. 다른 작업을 말씀해 주세요.
```

### 김배포 선임의 고충

> "배포 전략 차이가 뭐였더라? rolling이랑 blue-green… 위키 찾아보자."

위키를 열고, 검색하고, 문서를 읽고, 다시 콘솔로 돌아옵니다. **컨텍스트 스위칭의 비용.**

```
👤 김배포: rolling 배포랑 blue-green 차이가 뭐야?
🤖 AI: Rolling 배포는 인스턴스를 순차적으로 교체하는 방식이고, Blue-Green은
       새 환경을 완전히 준비한 후 트래픽을 한 번에 전환합니다. Rolling은
       점진적이라 리스크가 낮고, Blue-Green은 전환이 빠르지만 리소스가 두 배
       필요합니다.
```

**작업 화면을 떠나지 않고, 필요한 지식을 바로 얻습니다.**

## Episode 2. 이승인 팀장의 오후 — "승인"

### 쌓여가는 승인 큐

이승인 팀장은 오후 2시, 점심 미팅을 마치고 자리에 앉습니다. 승인 대기 큐가 몇 건인지부터 확인해야 합니다. 승인 페이지를 열고, 필터를 "pending"으로 바꾸고, 유형별로 몇 건인지 세어봅니다. 고위험 요청이 섞여 있는지 눈으로 하나씩 확인합니다.

> **이승인:** "지금 pending이 몇 건이지? config change는 따로 있나? 고위험 건은?"

세 가지 질문에 답하려면 필터를 세 번 바꿔야 합니다.

### AI 어시스턴트가 있다면

```
👤 이승인: 지금 승인 대기 몇 건이야?
🤖 AI: 현재 승인 대기 큐 현황입니다. 총 5건 대기 중이며, 유형별로
       임시 접근 2건, 설정 변경 2건, 데이터 작업 1건입니다.
       고위험 요청이 1건 있으니 우선 확인하시는 것을 권합니다.
```

**한 번의 질문으로 전체 현황 파악 + 우선순위 가이드까지.**

### 승인 처리를 시작합니다

```
👤 이승인: 승인 요청 확인해줘
🤖 AI: 필요한 정보가 모두 준비되었습니다.
       ┌──────────────────────────────────────┐
       │   Approval Queue Inbox               │
       │                                      │
       │   🔴 [HIGH] DB 스키마 변경 - catalog  │
       │   🟡 [MED]  임시 접근 - payments-api  │
       │   🟢 [LOW]  설정 변경 - checkout       │
       │                                      │
       │   [승인]  [보류]                       │
       └──────────────────────────────────────┘
```

큐 목록이 바로 Surface로 렌더링됩니다. 클릭 한 번으로 승인, 클릭 한 번으로 보류.

### 이승인 팀장의 고충 — 고위험 요청의 부담

> **이승인:** "이 요청 고위험인데… blast radius가 어디까지지? 승인해도 되는 건가?"

```
👤 이승인: 고위험 요청은 어떻게 처리해?
🤖 AI: 고위험 요청은 riskTone이 danger로 표시됩니다. 일반 요청보다 더 신중한
       검토가 필요하며, 영향 범위(blast radius)와 복구 방법을 반드시 확인한 후
       승인해야 합니다.
```

> **이승인:** "이건 일단 보류하고 추가 정보 받자. 보류하면 어떻게 되지?"

```
👤 이승인: 보류하면 어떻게 돼?
🤖 AI: 요청을 보류하면 즉시 거절되지는 않지만 실행이 중단됩니다. 보류 상태에서는
       추가 정보를 요청하거나 다른 승인자에게 위임할 수 있습니다. 요청자에게
       보류 사유가 전달됩니다.
```

**판단에 필요한 정보를 즉시 제공하여, 승인자의 의사결정 속도를 높입니다.**

### 도중에 배포 요청이 들어오면?

이승인 팀장이 승인 큐를 보다가 긴급 배포를 해야 할 상황이 생겼습니다. 기존이라면 탭을 전환하고, 배포 페이지로 이동하고, 처음부터 다시 시작합니다.

```
👤 이승인: 배포하고 싶어
🤖 AI: 어떤 서비스를 배포할까요?
       [payments-api]  [checkout]  [catalog-api]
```

**도메인 전환이 자연스럽게 이루어집니다.** 승인 → 배포 → 다시 승인, 어떤 조합이든 대화 흐름 안에서 해결됩니다.

## Episode 3. 박롤백 대리의 긴박한 밤 — "롤백"

### 새벽 2시, 알림이 울립니다

박롤백 대리의 폰이 울립니다. PagerDuty 알림 — `payments-api` severity HIGH 인시던트. 에러율 급등. 잠에서 깬 그는 노트북을 열고 콘솔에 접속합니다.

> **박롤백:** "지금 상황이 어떤 거지? 어떤 서비스에서 문제가 생긴 거야? 롤백 가능한 버전이 있어?"

기존이라면 — 모니터링 대시보드 확인, 인시던트 페이지 확인, 롤백 페이지로 이동, 서비스 필터, 버전 목록 확인. 새벽에 잠이 덜 깬 상태로 **최소 5분.**

### AI 어시스턴트가 있다면

```
👤 박롤백: payments-api 롤백 상태 알려줘
🤖 AI: payments-api는 현재 v2.3.18로 운영 중이며, severity high
       인시던트(INC-842)가 감지되었습니다. 추천 롤백 버전은 v2.3.16이며,
       총 2개 버전으로 롤백 가능합니다.
```

**현재 상태, 인시던트 정보, 추천 롤백 버전까지 한 번에.** 인시던트 대응에서 가장 중요한 것은 **속도**입니다.

### 롤백을 실행합니다

```
👤 박롤백: 롤백하고 싶어
🤖 AI: 어떤 서비스를 롤백할까요?
       [payments-api]  [checkout]  [catalog-api]

👤 박롤백: payments-api
🤖 AI: 필요한 정보가 모두 준비되었습니다.
       ┌──────────────────────────────────────┐
       │   Rollback Target List               │
       │                                      │
       │   v2.3.16 (stable, 추천)     [롤백]   │
       │   v2.3.15 (stable)          [롤백]   │
       │                                      │
       └──────────────────────────────────────┘

👤 박롤백: [이 버전으로 롤백] 클릭
🤖 AI: ──────── rolling back ──────── → ✅ recovered
```

### 박롤백 대리의 고충 — 새벽의 불안

인시던트 대응 중에는 판단력이 떨어집니다. 새벽이라 더 그렇습니다. "데이터는 괜찮을까?" "dry run이 뭐였더라?" 위키를 찾아볼 여유가 없습니다.

```
👤 박롤백: 롤백하면 데이터는 어떻게 돼?
🤖 AI: 롤백 시 코드 버전은 되돌아가지만, 데이터베이스 마이그레이션은 자동으로
       되돌아가지 않습니다. 스키마 변경이 포함된 배포의 경우
       backward-compatible 마이그레이션인지 먼저 확인해야 합니다.
```

```
👤 박롤백: dry run이 뭐야?
🤖 AI: Dry run은 실제 롤백 전에 시뮬레이션으로 검증하는 단계입니다. 환경 호환성,
       의존성 충돌, 트래픽 전환 가능 여부를 미리 확인합니다. 문제가 발견되면
       실제 롤백 전에 대응할 수 있습니다.
```

**긴박한 상황에서 즉시 답을 얻는 것.** 이것이 인시던트 대응 시간을 단축하는 핵심입니다.

### 롤백이 실패하면?

```
👤 박롤백: 롤백 실패하면 어떻게 해?
🤖 AI: 롤백이 실패하면 현재 상태가 유지됩니다. Dry run에서 실패했다면 다른
       버전으로 재시도할 수 있고, 트래픽 전환에서 실패했다면 수동 개입이
       필요합니다. 운영팀에 즉시 에스컬레이션하는 것을 권장합니다.
```

**최악의 상황에서도 다음 행동을 안내합니다.**

## Episode 4. 세 사람이 만나는 순간 — "도메인 간 전환"

### 현실의 DevOps는 한 가지 일만 하지 않습니다

김배포 선임이 배포를 준비하다가 승인이 필요한 걸 발견합니다.

```
👤 김배포: (배포 진행 중) 승인 요청 확인해줘
🤖 AI: (자연스럽게 승인 도메인으로 전환)
       필요한 정보가 모두 준비되었습니다.
       [Approval Queue Inbox Surface]
```

이승인 팀장이 승인 처리 중에 문제가 생긴 서비스를 발견합니다.

```
👤 이승인: (승인 큐 확인 중) 롤백 후보 알려줘
🤖 AI: (자연스럽게 롤백 도메인으로 전환)
       롤백 후보 현황입니다. payments-api에서 severity high 인시던트가
       감지되었으며...
```

박롤백 대리가 롤백 후 재배포를 해야 합니다.

```
👤 박롤백: (롤백 완료 후) 배포하고 싶어
🤖 AI: (자연스럽게 배포 도메인으로 전환)
       어떤 서비스를 배포할까요?
       [payments-api]  [checkout]  [catalog-api]
```

**탭 전환도, 페이지 이동도, 컨텍스트 유실도 없습니다.** 대화의 흐름 안에서 모든 도메인을 넘나듭니다.

## Before & After

| 기존 방식 | A2UI 어시스턴트 |
|-----------|----------------|
| 배포 이력 확인에 3분 (페이지 이동 + 필터) | **"마지막 배포 언제?" → 3초** |
| 배포 시작까지 7단계, 2분 | **대화 1~2턴, 10초** |
| 승인 현황 파악에 필터 3번 변경 | **"대기 몇 건?" → 한 번에 요약** |
| 도메인 전환 시 탭/페이지 이동 | **자연어 한 마디로 즉시 전환** |
| 지식 확인 시 위키/문서 검색 | **작업 화면에서 바로 질문** |
| 인시던트 대응 시 여러 화면 동시 확인 | **상태 + 추천 버전 + 실행까지 한 흐름** |
| 실수 시 뒤로 가기 → 처음부터 | **"아니 다른 걸로" → 즉시 정정** |

## 핵심 메시지

> **A2UI DevOps Assistant는 DevOps 엔지니어의 "클릭"을 "대화"로 바꿉니다.**
>
> 반복적인 네비게이션을 없애고, 컨텍스트 스위칭을 줄이며,
> 긴박한 순간에도 정확한 정보와 즉각적인 실행을 제공합니다.
>
> 72개 시나리오 — 배포 18건, 승인 17건, 롤백 16건, 공통 21건 — 을 통해
> 실제 DevOps 워크플로우의 모든 경로를 커버합니다.
