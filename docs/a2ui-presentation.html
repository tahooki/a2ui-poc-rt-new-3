Overview

Part 1 — Deploy

김배포 선임의 배포 일지

Platform Engineer. 도커 이미지 기반 배포 파이프라인을 운영하며, 매번 여러 단계를 거쳐야 하는 배포 프로세스를 담당합니다.

배포 한 번이 이렇게 복잡합니다

배포를 하려면 먼저 도커 이미지를 빌드하고, 레지스트리에 push한 뒤, 콘솔에서 이미지를 등록해야 합니다. 그 다음 배포 요청(Request)을 만들기 위해 서비스, 환경, CPU, 메모리, 전략 등을 하나하나 선택하고 입력합니다. 그리고 나서야 비로소 배포를 실행할 수 있습니다.

"이미지 등록하고, 리퀘스트 만들고, 실행까지... 3단계를 각각 다른 탭에서 해야 해. 입력할 게 너무 많아."

이미지 등록 화면에서 Repository, Tag, URI, Git Ref, Digest 등 8개 필드를 채우고, 배포 요청 화면에서 서비스, 환경, CPU, 메모리 등 13개 필드를 추가로 채워야 합니다. 한 번의 배포에 총 21개 입력과 여러 번의 클릭이 필요합니다.

🐳
도커 이미지 기반 3단계 배포

이미지 등록, 배포 요청 생성, 실행이 별도의 탭과 폼으로 분리되어 있습니다.
총 21개의 입력 필드
이미지 등록 8개 + 배포 요청 13개. 매번 수동으로 채워야 합니다.
이전 배포 참고가 번거로움
같은 서비스를 배포했던 설정을 보려면 이력 페이지로 이동해서 하나하나 찾아야 합니다.
실수하면 처음부터
서비스나 환경을 잘못 선택하면 뒤로 가기 후 다시 입력해야 합니다.

Part 2 — Approval

이승인 팀장의 오후

DevOps Team Lead. 임시 접근, 설정 변경, 데이터 작업 등 다양한 승인 요청을 관리합니다.

쌓여가는 승인 큐

점심 미팅을 마치고 자리에 앉으면, 먼저 승인 대기 건수부터 확인합니다.

"지금 pending이 몇 건이지? config change는 따로 있나? 고위험 건은?"

세 가지 질문에 답하려면 필터를 세 번 바꿔야 합니다. 고위험 요청은 눈으로 하나씩 확인해야 합니다.

Insight

이렇게 만든 이유

A2UI를 여러 버전으로 구축하고 다시 만들면서 발견한 어려움과, 그에 따른 설계 결정입니다.

A2UI 구축의 어려운 점

Challenge 1
백엔드 작업의 부수적 부담
A2UI에 필요한 정보를 받아오는 백엔드, 버튼 액션에 맞는 백엔드 행동을 새롭게 만들거나 설계에 맞춰 넣어줘야 합니다.
Challenge 2
기존보다 더 좋아야 하는 높은 기준
A2UI가 기존 페이지보다 더 좋아야 하며, Chatbot에서 글로 보여주는 것보다 더 좋은 사례여야만 A2UI의 가치가 있습니다.
Challenge 3
사용자에게 직접 만들게 하는 한계
A2UI를 사용하는 사용자가 A2UI에 대해 학습하고, 더 좋은 UIUX를 연구해서 등록하게 하는 것은 큰 어려움이 있습니다.
따라서, 직접 등록이 아닌 솔루션으로 풀기로 했습니다.
사용자가 직접 Template을 만들게 하는 것이 아니라,
솔루션 차원에서 직접 설계하여 템플릿 수준으로 제공하기로 결정했습니다.

이 접근의 장점

예측 가능한 품질 확보
어떤 값이 나올지 예측 가능해져, 고객에게 전달하는 A2UI 품질을 확보할 수 있습니다.
사용자 학습 비용 절감
A2UI를 직접 필요한 부분을 솔루션하여 설계해줌으로써, 사용자가 무엇을 A2UI로 만들어야 할지 고민하는 시간을 줄여줍니다.
Value Proposition

A2UI는 언제 가치가 있나요?

다음과 같은 상황에서 A2UI를 도입하면 사용자의 편의성을 확보하여 AI Chatbot을 더욱 가치있게 만들 수 있습니다.
기존 시스템 수정이 어려울 때
레거시 시스템을 건드리지 않고, Chatbot 레이어에서 새로운 UX를 제공합니다.
기존 시스템이 복잡할 때
여러 페이지에 흩어진 정보를 하나의 Surface로 모아 인지 부하를 줄입니다.
자주 쓰는 기능을 묶을 때
반복되는 워크플로우를 대화 한 줄로 압축하여 작업 속도를 높입니다.
A2UI는 DevOps 엔지니어의 "클릭"을 "대화"로 바꿉니다.
반복적인 네비게이션을 없애고, 컨텍스트 스위칭을 줄이며,
긴박한 순간에도 정확한 정보와 즉각적인 실행을 제공합니다.
